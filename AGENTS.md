# AGENTS.md

Обязательные рабочие правила для AI coding agents в репозитории `madina-platform`.

## Работа с текущим состоянием

1. Всегда сначала изучай фактическое текущее состояние файлов, которые собираешься менять.
2. Никогда не опирайся на предполагаемую или старую версию кода.
3. Не повторяй изменения, которые уже присутствуют в текущем файле.
4. Перед изменением сначала определи минимальный необходимый scope.
5. Не выполняй массовый рефакторинг без явной необходимости.
6. Не изменяй файлы вне области текущей задачи без обоснованной технической необходимости.

## Архитектура и переиспользование

7. Сохраняй существующую архитектуру monorepo и package boundaries.
8. Используй существующие shared abstractions и компоненты из `@madina/shared`, `@madina/core` и `@madina/ui` вместо дублирования.
9. Перед созданием нового компонента, типа, сервиса или utility сначала проверь, нет ли уже подходящего существующего.
10. Не перемещай business-domain logic в shared packages только ради удобства UI.
11. Сохраняй существующий стиль TypeScript/React и форматирование проекта.
12. Не меняй package versions, lockfile, dependencies или tooling без явной задачи.

Текущая структура проекта:

- `apps/crm` — активное CRM-приложение.
- `packages/core` — core/business services.
- `packages/shared` — shared utilities/types.
- `packages/ui` — shared UI components.

## Git и безопасность изменений

13. Не выполняй destructive Git operations.
14. Никогда не выполняй `git commit`, `git push`, `merge`, `rebase` или `reset` без явного разрешения пользователя.
15. После изменений сначала проверь `git diff` и убедись, что нет неожиданных изменений.
16. Выполняй `git diff --check`.

## Проверки

Используй фактические команды проекта:

```sh
pnpm test
pnpm build
git diff --check
```

17. Для значимых изменений запускай `pnpm test`.
18. Для изменений, способных повлиять на сборку или TypeScript, запускай `pnpm build`.
19. Если test или build упали, найди причину и исправляй только то, что относится к текущей задаче.
20. Не скрывай failing tests или build errors.

## Завершение задачи и неоднозначности

21. В конце каждой задачи дай краткий отчёт:
   - что изменено;
   - какие файлы изменены;
   - какие проверки выполнены;
   - результаты test/build;
   - есть ли оставшиеся риски или вопросы.
22. Если задача неоднозначна или изменение затрагивает архитектурное решение, сначала остановись и сообщи об этом, а не выбирай архитектуру самостоятельно.
